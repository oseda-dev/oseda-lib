Context Free Grammars (CFGs)

  • A CFG is defined as a 4-tuple
  • V: Variables (non-terminal placeholders)
  • T: Terminals (concrete strings)
  • P: Productions (replacement mappings from Variables to Variables/Terminals)
  • S: Start (A beginning for strings to start deriving)

CFGs

  • Easier to see an example of
  • V = { S }
  • T = EMPTY_STRING
  • P = { S -> (S)S | EMPTY_STRING }
  • S = S
  • Start with S, replace S with production rules

Lisp's Grammar

  • Very simple
  • "Backus-Naur Form" is a grammar "notation" that makes this easy to see
  • Mix of Regex (*, +, etc) with formal CFG
1. s-expr  ::= atom | list
2. list   ::= "(" s-expr* ")"
  • Procedural languages have more complex grammars
  • When you go on to parse Lisp, this will be useful

Parsing

  • Once the rules are defined
  • Source is "lexed" into tokens/symbols (!)
  • Symbols are then parsed into a tree
  • Production rules in the grammar
  • Map directly to nodes in the tree
  • Terminals map to leaf nodes

Syntax Trees

  • Concrete Syntax Trees represent the raw source
  • Usually converted to an Abstract Syntax Tree
  • (dropping non-essential information like {, }, ;, etc)
  • Optimizations usually occur at the AST level

AST example

  • Euclidean Algorithm
  • Straight from Wikipedia
while b != 0:
    if a > b:
        a := a - b
    else:
        b := b - a
return a

Execution

  • Once you have a syntax tree, you can start parsing the code
  • Walk the AST (pre-order or post-order)
  • Simple AST walking is slow, but it IS how CommonLisp handles this
  • Each Node is a cons cell
  • You could compile into a lower representation
  • Or attempt to optimize AST walking

Summary

  • This is a generalized process
  • Most languages tweaks a few ideas about how parsing/execution works
  • ALL* of them at least need:
  • Lexed into tokens/symbols
  • Built into an AST
  • Executed (at some level)
  • "Symbols step" will be important for next time
